# 桌面智能体走错一步后，还能把任务做完吗？

2026 年 11 月 27 日。研究对象是 THUDM/SCALE-CUA 发布的 Qwen3-VL-8B OSWorld SFT 模型。SFT 指用示范轨迹做监督微调。我们计划在 8 张 A100 上，用 256 道筛过的官方训练题比较强化学习方法。我们可以用这套资源回答两个问题。**在一段长任务的中途，哪些动作会实质改变最终成功率？训练时知道这些差异，能否让模型在一次独立尝试里表现得更好？** [SCALE-CUA 作者仓库](https://github.com/THUDM/SCALE-CUA) · [本项目实验排期](../docs/2026-11-27-桌面强化学习筛题与实验排期.md)

## 一、为什么从中途决策入手

我们的 SFT 模型在 OSWorld 361 道题里有 358 道取得有效评分，均分 **44.32%**。限定在训练划分的 77 道跨应用原题，均分降到 **10.39%**。其中 69 道得零分，62 条零分轨迹记录了至少 50 个动作。另一批筛选中，394 道候选各有四次有效终局评分，176 道出现过分差。这说明同一模型对同一指令有时能走出不同结局。仅凭这批日志，还定位不了哪一个动作造成了分差。[本项目的 SFT 分项和筛选记录](<../docs/CUA-RL Dataset OnePage.md>)

设想模型已经从两份文件里查到正确数值，准备回填成绩表。它可能写入正确学生的行，也可能把答案写进紧邻的一行。两个窗口看起来都像“做了九成”，剩余工作却可能相差很远。**PPO**（Proximal Policy Optimization）训练负责选动作的策略，同时用一个 **critic**（价值模型）预测按当前策略继续做能得多少分。**Turn-PPO** 把一次看屏幕、生成回复并执行动作当作一个决策单位。如果 critic 给上述两种局面同样的高估值，就值得检查它究竟看到了什么，以及这个错误是否真的影响策略。[Turn-PPO 原论文，实验环境为 WebShop 和 Sokoban](https://aclanthology.org/2026.findings-eacl.328/)

## 二、OS-Omni 给了我们一个比“再跑一遍 OSWorld”更有区分力的测试

OS-Omni 的 v1 论文于 **2026 年 11 月 25 日**提交。正式清单合计 **300 题**，包括 Linux、Windows、macOS、iOS、Android、Web 各 48 题，以及 12 道桌面与 Android 联动题。Web 组使用 Linux 虚拟机上的浏览器，跨设备组在同一屏幕里操作桌面和手机窗口。评分器可以读取保存后的文件、应用数据库或服务端记录，再逐项核对结果。正式题数和版本应以 GitHub 的 v1 清单为准。[论文](https://arxiv.org/abs/2611.34232) · [v1 官方题单](https://github.com/OS-Copilot/OS-Omni/blob/649139ced6dfd10bd86198e2ae314fabd819e6db/tasks/v1/manifest.json) · [评分协议](https://arxiv.org/html/2611.34232v1#A3.SS7)

**看一道真题。** 在预算复核题里，模型先在 Android 的 Markor 中修正一份 16 行 CSV，转到 Linux，在 LibreOffice Calc 里建六张工作表，通过公式做差额和汇总，再把桌面算出的数字写回手机，并为符合条件的项目创建待办。假如模型只复制了 15 行，它仍能顺利建表、算总和、创建待办。单看“是否进入了下一个应用”，每一步都像有进展。对照手机源文件和最终工作簿，可以查出哪一行的错误传到了最后。再回看操作记录，才能知道模型有没有回头核对来源。[预算复核题原文与评分配置](https://github.com/OS-Copilot/OS-Omni/blob/649139ced6dfd10bd86198e2ae314fabd819e6db/tasks/v1/cross_device/linux_android_budget_review_hard.yaml)

论文报告的人类平均交互步数是 **67.54**，引用的 OSWorld 参考值为 **15.0**。这是两项人类研究的操作统计，不能直接换算成我们的模型调用数或 GPU 工时。另一个容易看漏的细节是，论文表 1 的最佳模型按七组等权计算为 **68.5%**，人类参考为 **77.3%**。12 道跨设备题合计与 48 道 Linux 题权重相同。表中另一款 9B 模型 300 题全败，这让我们尤其要留意 8B 在这个基准上是否有足够多成功例来区分两种方法；SCALE-CUA 的表现仍须实测。[论文表 1 及统计口径](https://arxiv.org/html/2611.34232v1#S4)

作者还公开了逐项核查评分和题意的记录。比如 `AND-003` 指出，某道 Delta Chat 任务的初始化代码会打开 OpenNote，公开审计将这项差异标为已确认。它和我们测恢复的关系很直接：如果错应用是环境打开的，把它算成模型自己的失误就会高估策略错误。复用 OS-Omni 时应锁定任务和评分器版本，保存初始截图、系统错误和有效评分数。下面的外部评测建议依据仓库版本 `649139c`。[作者的审计表](https://github.com/OS-Copilot/OS-Omni/blob/649139ced6dfd10bd86198e2ae314fabd819e6db/scan.csv)

**我建议把 OS-Omni 留作外部评测。** 先用非计分样例验证 Linux runner 的截图、输入、重置和评分接口。模型与参数冻结后，用 SFT、原版 GRPO、表现最好的 PPO 各跑同一批 **48 道 Linux 题**，每题一次，逐题配对。再从 12 道跨设备题中的 **6 道 Linux + Android** 检查跨设备行为，注明每多做对一题就是 16.7 个百分点。官方主协议用截图和最近三步历史，单平台上限 300 步，跨设备上限为 300–650 步；若沿用本项目的 50 轮预算，则单列为限制预算实验。仓库公开了 runner、任务和评分器，发布包没有随附已安装应用的 VM 快照，接入成本需实测。[官方运行说明](https://github.com/OS-Copilot/OS-Omni#running-v1) · [Linux QEMU 指南](https://github.com/OS-Copilot/OS-Omni/blob/649139ced6dfd10bd86198e2ae314fabd819e6db/docs/linux_headless.md) · [论文附录 D](https://arxiv.org/html/2611.34232v1#A4)

还有一个适合后续追问的基准。**OSWorld 2.0** 收录 108 个长工作流，专门覆盖信息在执行中到达、约束藏在先前操作里、任务需要跨来源核对等情形。如果模型在 OS-Omni 上常常提前结束，可以用这里的案例进一步区分“忘了用户的约束”和“没有检查产物”两类失败。[OSWorld 2.0 论文](https://arxiv.org/abs/2606.29537)

## 四、从其他专业借来三个能实际测的问题

### 从这里继续，还有多大机会成功？

统计物理里的 **committor** 回答一个朴素的问题。从当前状态出发，系统会先到达两个终点中的哪一个？先到达 B 的概率，就是这个状态的 committor。借到二值桌面任务里，可以固定模型、输入历史和剩余步数，把“在预算内完成任务”的概率作为中间状态的价值。这个类比给了一个测量方法。回到同一个尚未保存的工作簿，让冻结模型独立续跑，最后统一检查磁盘上的文件。四次续跑都失败，只说明这次观察到 0/4；更强的策略或更长的预算有可能救回来。[有限时间的 transition path theory](https://link.springer.com/article/10.1007/s00332-020-09652-7)

SpaceX 的 Crew Dragon 测试有一个值得借用的习惯。项目负责人在 NASA 访谈里谈到，测试还要检查团队对系统在不同条件下的**预测**能否成立。我们可以把同一训练任务准备成三个起点，分别是正常工作表、外部弹窗抢走焦点，以及模型自己在上一步选错了学生的行。保留对应的真实操作历史，记录 critic 预测与独立续跑的最终结果。第三种情况更能说明模型能否挽回自己的判断失误。工程上可借鉴 Go-Explore 保存并返回中间状态的办法，先从不依赖外部服务的本地文件任务做起。[NASA 对 SpaceX 的访谈](https://www.nasa.gov/podcasts/houston-we-have-a-podcast/the-spacex-crew-dragon/) · [Go-Explore](https://www.nature.com/articles/s41586-020-03157-9)

### 模型犹豫的地方，值得多试一次吗？

**Entropy（熵）**衡量模型的概率分布有多分散。模型可以很犹豫该写哪种动作语法，几种写法却会按到同一个按钮。它也可以非常确信该覆盖原文件，尽管“另存为副本”对这道题至关重要。数学推理研究发现少数高熵 token 对训练很有用；ARPO 已经用工具调用后的熵变化分配分支，DART-GUI 又把高熵选步用到了桌面。另一条线是 *semantic entropy*，先把表达方式不同、意义相同的答案归在一起。迁移到 GUI 时，“同一个效果”要结合当前应用判断。[高熵 token 研究](https://arxiv.org/abs/2506.01939) · [ARPO](https://arxiv.org/abs/2507.19849) · [DART-GUI](https://arxiv.org/abs/2509.23866) · [Semantic entropy](https://www.nature.com/articles/s41586-024-07421-0)

可以在同一批决策处比较三样东西。第一，模型生成**动作内容**时的 token 熵，解释文字另算；只有一个已生成 token 的概率时，无法重建整个分布。第二，在同一张屏幕和同一段历史上采样多个候选动作，按预期效果人工归组，例如在已命名的本地文档上，点保存图标与按 Ctrl+S 可以同组。第三，在独立恢复的桌面上分别执行两个候选动作，让同一个模型接手，测两种选择最终成功率相差多少。前两项能否预测第三项，是有结果也可能被推翻的假设。尤其要抽到**低熵但很自信地做错**的位置。

### 模型能看到哪种错误？

OpenAI 的 Codex 工程案例让 agent 看到运行中的应用、浏览器状态和日志。Anthropic 的评测文章区分执行记录与最终环境结果。Grok Bot 的产品案例则展示了在持久电脑和多个应用中连续工作的使用方式。三个来源分别能帮助我们设计观测、评分和任务；从产品行为推断其内部 PPO 配方没有足够依据。[Codex 工程实践](https://openai.com/index/harness-engineering/) · [Anthropic 评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [Grok Bot](https://x.ai/news/introducing-grok-bot)

桌面截图只暴露了部分状态。一张表在两个窗口里可以长得完全一样，底层却是不同文件。可以先做两组实验。第一组给所有模型相同的截图历史，测它们是否会主动核对文件名。第二组只给训练时的 critic 增加当前文件路径或修改标记，执行动作的模型仍只看屏幕。价值预测和单次成功率都要测。若只给 actor 增加局部放大工具，则另列为视觉对照，同时记录视觉 token 和操作次数。这样能区分感知受限、历史遗忘和动作价值学错三种情况。[部分可观测环境中的 asymmetric critic](https://arxiv.org/abs/2105.11674) · [可主动选择观察区域的 GUI 研究](https://ericxl.github.io/foveated-screen-perception/)

## 五、8 张 A100 上先做什么

**保留已有主线。** 用冻结的题单从同一 SFT 权重启动 SCALE-CUA 原版 GRPO、普通 PPO、Turn-PPO。GRPO 用同一题多次尝试的相对得分更新策略。普通 PPO 提供 token 级对照，Turn-PPO 用整轮 GUI 决策估值。GiGPO 用来检验自然重复状态能提供多少信号。优先把少量分支预算用于检验 Turn-PPO 的 critic；Gamer 的 TA-GRPO 留给能独立检查阶段产物的题。先完成 16 与 24 桌面并发的比较，才用实测吞吐排正式机时。[已约定的排期与预算](../docs/2026-11-27-桌面强化学习筛题与实验排期.md) · [Gamer 的阶段训练方法](https://arxiv.org/html/2611.18397v1#S4)

| 首轮诊断 | 具体做法 | 能据此决定什么 |
|---|---|---|
| 验证桌面恢复 | 选 16 个训练侧任务家族，每家族选一题，预先确定早、晚各一个决策位置，共 32 处。保存 VM、模型可见历史和剩余步数。重放同一动作，核对当前文件、未保存修改、窗口焦点与评分。预选位置未到达时记录原因。 | 恢复会丢应用内存或改变服务端状态的任务暂不做分支。记录每次恢复耗时及失败比例。 |
| 估计当前位置的价值 | 冻结一个带 critic 的 PPO checkpoint，每处自然续跑 4 次，最多 **128 条**。由模型自己选第一步。按任务家族留出一部分位置只做评估。 | 用独立的二值成败结果计算预测概率的均方误差（Brier score），另报部分得分任务的回报误差。若模型预测七成成功，检查类似状态合起来能否接近七成。 |
| 估计换动作的后果 | 从中事先选 8 处，每处选两个效果不同的动作，每个动作从恢复后的桌面执行，再由同一模型接手，每个动作独立重复 4 次，剩余步数相同，最多 **64 条**。随机位置和高熵位置都要有，记下入选方式。 | 这批标签回答“先做 A 或 B 分别会怎样”，不能直接充当自然策略的状态价值。比较两动作的成功差、环境噪声和估计区间。8 处用来判断是否值得扩样。 |
| 决定是否用于训练 | 先比较原版 Turn-PPO、随机位置额外续跑、FOCUS 式选位置续跑。训练用当期冻结策略重新采集，三组核算相同的总 GUI 交互预算，记录 GPU 小时、有效轨迹数、恢复与重试开销。 | 首要指标是留出题的 **pass@1**，即每题只给一次独立尝试。其次看相同错误起点的恢复成功率、critic 校准和训练成本。若只改善估值，论文结论就限于估值。 |

首轮诊断上限为 **192 条中途续跑**，另计到达分支点的前缀、重放检查和环境重试。四次续跑不足以给单个动作定性，区间按任务家族成组计算。如果模型经常犯某类错误，屏幕或历史里有线索，换一个动作确实更常成功，而且在新任务上也能识别这些时刻，这类错误就值得投入下一批算力。届时我们才有理由说，新增训练信号教会了模型一种可以带到新任务上的能力。
